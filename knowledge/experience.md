# 經驗紀錄

## 2026-11-20：用原生技術完成小型點餐流程

### 做法與觀察

- 單頁作品用資料陣列保存飲品，再由同一份資料產生分類菜單，新增品項時不用為每張卡片重複寫事件處理。
- 把甜度、冰塊、杯型、配料一起組成客製品項識別鍵；相同飲品且選項完全相同時合併數量，不同客製方式則分開計價。
- 價格以「飲品基礎價格 + 杯型加價 + 配料加價」集中計算，購物車用每杯單價乘數量得出小計，較容易檢查。
- 先完成加入、增減、移除、總價、結帳清空的完整操作循環，再考慮促銷等額外功能，有助於控制課堂作品大小。
- 用原生 HTML/CSS/JavaScript 不需安裝或建置工具，適合尚未知道課程框架要求時先交付可操作雛形；若課程指定技術不同，再移植資料與計價規則。

### 未來可套用範圍

- 小型餐飲／商品目錄、客製選項與購物車原型。
- 課堂作品或靜態前端展示，尤其是尚未需要帳號、後端或付款的情境。
- 對規格尚不明確的短期專案，先以可替換的資料模型和明確核心流程做雛形。

### 限制與待補

- 目前資料寫在 JavaScript 中，重新整理會清空購物車；尚未接資料庫、登入、付款或訂單保存。
- 已執行 Node.js 語法檢查與 Git diff 空白檢查；瀏覽器預覽被目前瀏覽器工具的本機 `file:` 網址政策阻擋，尚未完成實際視覺檢查。
- 課程指定語言、繳交期限及評分規準仍未知，需拿到課程資訊後再核對功能與呈現方式。

## 2026-11-20：替無建置工具的前端加上回歸測試

### 做法與觀察

- 使用 Node.js 內建 `node:test`、`assert`、`vm`，以小型假 DOM 呼叫現有事件處理器，無需安裝測試框架或改成打包流程。
- 覆蓋菜單分類、客製選項對應加價、同客製品項合併、增減數量、移除與結帳清空；這些是價格錯誤最容易出現的核心互動。
- 假 DOM 測試能驗證 JavaScript 狀態和輸出字串，但不能取代瀏覽器實際版面、原生選單操作或螢幕閱讀器檢查，文件中需分開說明兩者的涵蓋範圍。

### 未來可套用範圍

- 無框架的靜態網頁或小型課堂專案，特別是希望維持零依賴又要檢查購物車、表單等互動的情境。
- 先以核心資料與操作流程建立少量回歸測試，之後修改版面時可快速確認商業規則沒有回歸。

## 2026-11-20：讓動態控制項提供明確的讀屏名稱

### 做法與觀察

- 分類按鈕用 `aria-pressed` 同步目前篩選狀態；加入、增加、減少、移除等重複操作按鈕把飲品名稱放入無障礙名稱，避免讀屏只聽到一串相同的「加入購物車」。

- 用既有 Node.js 回歸測試檢查產生的標籤與分類狀態，讓基本無障礙語意隨互動修改一起被驗證。

### 未來可套用範圍

- 動態更新頁面內容時，為讀屏使用者提供明確控制項名稱與狀態提示。

## 2026-11-20：為純前端專案接上 GitHub Pages

### 做法與觀察

- 靜態網站可用單一 GitHub Actions 工作流程部署：checkout、configure-pages、上傳 Pages artifact、deploy-pages。
- 對不需編譯的原生前端，只把 `index.html`、JavaScript、CSS 複製到 `_site` 後上傳，避免把規劃文件與測試也公開在網站路徑中。
- workflow 對 `main` 分支 push 與手動觸發；部署工作只給 `contents: read`、`pages: write`、`id-token: write`，並使用 `github-pages` environment。
- 建立 workflow 還不等於網站已發布；repository Pages source 必須選 GitHub Actions，之後仍要檢查 Actions 執行結果和實際網址。

### 未來可套用範圍

- 原生 HTML/CSS/JavaScript 或其他無伺服器靜態專案。
- 課堂作品、作品集、文件站等可由 `main` 自動部署的公開網站。

### GitHub 身分驗證注意事項

- GitHub connector 可讀取個人檔案不代表瀏覽器或本機 Git CLI 已具備 repository 寫入能力；執行發布前要分別確認 connector 權限、瀏覽器登入狀態和 Git push 認證。
- 未登入時可先完成本地 workflow 與部署檔案，再交由使用者自行登入，避免索取或處理密碼、驗證碼。

**未來適用範圍：** 需要同時用 GitHub 網頁設定、GitHub Actions 與本地 Git 推送的專案。

### 發布驗證結果（2026-11-20）

- repository 建立後先把 Pages source 設為 GitHub Actions，再推送 workflow 與網站；首輪 Action 執行成功並取得公開網址。
- 以線上頁面完成最小 smoke test：首頁內容出現、加入一杯基本款能更新數量和 $35 小計、模擬結帳顯示摘要並清空購物車。
- 僅有 workflow 綠燈不足以證明網站體驗正常；應再直接載入部署網址並走過一個核心使用流程。

**未來可套用範圍：** 靜態前端課堂專案、個人展示頁與任何部署後可用少量互動確認核心體驗的 GitHub Pages 專案。

## 2026-11-27：替靜態菜單加入搜尋與購物車保存

### 做法與觀察

- 搜尋欄與既有分類條件採交集篩選，搜尋飲品名稱、風味描述和分類；清單為空時明確提供提示。這樣保留分類導覽，又不需複製第二套菜單狀態。
- 無後端的小型購物車可用 `localStorage` 保存 JSON，在載入時檢查欄位型別與數量，避免無效資料破壞畫面；新增、數量更動、移除與結帳清空都要同步保存。
- 將儲存讀寫包在 `try/catch`，讓瀏覽器停用儲存時點餐流程仍可使用。這只保護互動不中斷，並不提供備份、跨裝置同步或防竄改。
- 使用 Node.js 假 DOM 測試搜尋結果、無結果提示、購物車重新載入及結帳清除；仍需另行檢查實際手機版面和瀏覽器儲存行為。

### 未來可套用範圍

- 小型商品目錄需要同時支援分類與文字搜尋的靜態網站。
- 沒有帳號或後端，但使用者希望重新整理後保留暫存表單、購物車或篩選偏好的原型。
- 需要先驗證資料格式、並能在瀏覽器不允許儲存時降級運作的前端功能。

## 2026-11-27：保存有限筆數的前端訂單紀錄

### 做法與觀察

- 模擬結帳成功時，從購物車複製訂單摘要並記錄時間、品項、杯型、數量與總額；獨立於購物車保存，避免結帳清空時一併失去收據資料。
- 對課堂原型限制保留最近五筆，避免本機資料無上限累積；顯示時間使用瀏覽器本地格式，資料保留 ISO 時間字串。
- 訂單紀錄只供同一瀏覽器展示，不能視為正式訂單、付款憑證或可靠帳務來源。若需求升級為跨裝置查詢或營運訂單，應移至有驗證及備份的伺服器端儲存。
- 回歸測試應確認結帳建立摘要、重新載入可恢復、購物車仍正確清空；真實瀏覽器的 localStorage 行為仍需單獨檢查。

### 未來可套用範圍

- 無登入、無後端的教學原型，用來展示結帳後摘要或最近操作紀錄。
- 小型前端工具保存有限筆數的本機歷史，例如轉換紀錄、最近搜尋或草稿。
- 需求仍在驗證階段、且資料只需在單一瀏覽器暫存的可丟棄紀錄。

## 2026-11-27：從本機訂單歷史重建購物車

### 做法與觀察

- 若要支援再次點單，結帳時需保存每個品項的識別鍵、客製選項、單價與數量；只保存顯示文字不足以重建精確訂單。
- 再次點單沿用購物車既有識別鍵，將相同客製品項數量相加，避免出現重複列；重新加入購物車不應改動歷史訂單本身。
- 歷史資料可能早於新欄位格式，只有具備必要識別資訊的紀錄才提供一鍵重建，舊紀錄仍可閱讀。
- 回歸測試應涵蓋歷史資料跨重新載入、客製選項恢復與和現有購物車合併後的總價。
- 推送後再用隔離的瀏覽器資料走一次線上結帳與再次點單，可驗證 Pages 實際版本；測試資料放在短期隔離工作階段，避免混入平常瀏覽資料。

### 未來可套用範圍

- 保存在瀏覽器的最近操作、表單草稿或購物清單，需要從舊紀錄重複建立目前狀態。
- 可重複執行且條目有穩定識別鍵的前端工作流程，例如重複訂購、最近搜尋或快捷設定。

## 2026-11-27：用收藏清單快速重用常選項目

### 做法與觀察

- 以穩定的菜單項目 ID 保存收藏，而非保存完整飲品資料；菜單價格或文字調整時，收藏仍能對應目前的項目。
- 收藏按鈕使用 `aria-pressed` 表達切換狀態，並提供可讀的收藏／取消收藏標籤；獨立的收藏篩選可與既有關鍵字搜尋組合使用。
- localStorage 內容需解析成陣列並只接受仍存在菜單中的 ID；儲存不可用或資料損壞時，回退為空收藏不影響點餐。
- 回歸測試驗證收藏跨載入、篩選結果、取消收藏後空狀態，以及收藏清單保存內容。

### 未來可套用範圍

- 靜態購物、菜單或目錄頁面中，使用者希望快速回到常選項目，又不需要帳號同步的情境。
- 原生前端原型內的收藏／釘選功能；若未來需要跨裝置同步，再評估登入和後端儲存。

## 2026-11-27：讓 Pages 部署重跑使用獨立 artifact 名稱

### 做法與觀察

- `upload-pages-artifact` 與 `deploy-pages` 都提供 artifact 名稱參數；設定時兩邊必須一致。
- 對同一個 workflow run 重跑時，舊 attempt 的 artifact 可能仍存在。讓名稱包含 `${{ github.run_attempt }}`，並讓部署步驟選取同一名稱，可避免重跑時因找到多個 `github-pages` artifact 而失敗。
- 公開 REST artifact 清單可見，不代表 Pages deploy action 使用的 artifact 索引已同步；只輪詢 REST 清單仍可能讓部署查詢到 0 個結果。
- 將上傳和部署拆成兩個 job，並以 `needs: build` 建立 job 邊界，符合官方建議的 build/deploy 模式，也給 artifact 服務完成索引的時間；以 attempt 專屬名稱並在 deploy job 指定相同名稱，隔離同一 run 的重試產物。
- 診斷部署失敗時查看每個 attempt 的上傳與部署日誌，辨認是 artifact 不存在、重複或產物內容問題，再對症修正。

### 未來可套用範圍

- 使用 GitHub Pages 官方 actions 部署靜態網站，且允許手動或自動重跑 workflow 的專案。
- 同一 workflow 會為部署產生多個候選 artifact、需要明確選取本次執行產物的 CI/CD 流程。
